## 1. Goal recap

Silenced all four categories of build/runtime warnings that appeared after T-30 manual verification: Husky `install` deprecation, `z` re-export deprecation in content config, `FormEvent` type deprecation in Search component, and `[router]` route collision warnings from the `redirects` block.

## 2. What changed

- **`package.json`** — `scripts.prepare`: changed `"husky install"` to `"husky"` (Fix 1: Husky 9.1+ deprecated the `install` subcommand).
- **`src/content.config.ts`** — import line: removed `z` from the `astro:content` import; added `import { z } from 'astro/zod'` (Fix 2: `z` re-exported from `astro:content` is deprecated; `astro/zod` is the canonical non-deprecated path per Astro 6 type declarations).
- **`src/components/Search.tsx`** — line 29: changed `React.FormEvent<HTMLInputElement>` to `React.ChangeEvent<HTMLInputElement>` (Fix 3: React 19 deprecated `FormEvent` for `onChange` input handlers; `ChangeEvent` is semantically correct).
- **`astro.config.mjs`** — deduplicated the `redirects` block: dropped the 2 trailing-slash-stripped duplicates (`/posts/1`, `/tips/1`) and kept only the trailing-slash form (`/posts/1/`, `/tips/1/`) (Fix 4: under `trailingSlash: 'ignore'` the two variants of each entry resolve to the same logical route, which Astro 6 treats as a duplicate static route definition).

## 3. Why this approach

This task implements the "Build & runtime warnings cleanup" requirement from the Phase 3 post-T-30 follow-up fixes. No design §5/§6 risk register entries are impacted.

Fix 1: Husky's own migration guide states that `husky install` is superseded by bare `husky` in v9.1+; no alternatives exist.

Fix 2: The Astro 6 type declaration at `astro/types/content.d.ts` line 17 explicitly says "Use `import { z } from 'astro/zod'` instead." `astro:schema` is also deprecated (confirmed via `astro/client.d.ts` line 154). The fallback `import { z } from 'zod'` would also work but `astro/zod` is the official Astro-managed re-export that ensures version alignment with Astro internals.

Fix 3: `React.FormEvent` for `onChange` handlers was always semantically incorrect; `React.ChangeEvent` is the purpose-built type for input change events. The handler only reads `e.currentTarget.value`, which is available on both types.

Fix 4 (deduplicate the redirect entries): The `[router]` warning text was `The route "/posts/1" is defined in both "/posts/1" and "/posts/1/". A static route cannot be defined more than once.` The collision is between the two trailing-slash variants of the **same redirect declaration** — under `trailingSlash: 'ignore'`, Astro 6 normalises `/posts/1` and `/posts/1/` to a single logical route, so declaring redirects for both keys is a duplicate definition. There is no `[...page]` route in this codebase; page 1 is explicitly excluded from `src/pages/posts/[slug]/index.astro`'s `getStaticPaths` (it is served by `src/pages/posts/index.astro`). Removing the redirects entirely (the original v1 fix) was therefore wrong — it caused `/posts/1/` and `/tips/1/` to 404. The correct fix is to keep one redirect per logical path. The trailing-slash form is selected because Astro emits the static redirect HTML to `dist/posts/1/index.html` (i.e. `<dir>/index.html`) for that key, matching the project's prevailing trailing-slash URL pattern and the QA pass criterion that `dist/posts/1/index.html` exists.

- Defect file: `defects/T-33-D1.md`

Without redirects, nothing serves `/posts/1/`, so it 404s.
- Fix: Restored the `redirects` block in `astro.config.mjs` with **single entries per logical path**, retaining the trailing-slash form (`/posts/1/`, `/tips/1/`). Astro emits these as meta-refresh redirect stubs at `dist/posts/1/index.html` and `dist/tips/1/index.html`. The dev server returns HTTP 301 → 200 for both URLs.
