## 3. Why this approach

This task implements the operational scaffolding for the campaign described in design
§1 (success criteria), §3 (worktree-per-task strategy), and §5 (uniform verification
protocol). T-00 specifically establishes the visual baseline referenced in success
criterion §1.5 ("local dev server renders correctly on these routes") and the audit
baseline referenced in §5 step 6 ("no new High/Critical entries vs baseline").

Alternatives considered and rejected:

- **Skipping the audit baseline** because yarn 1's `audit` output is noisy — rejected:
  the file is only consulted as a delta source, so verbosity is acceptable, and it
  lets later tasks (T-20, T-22, T-26 in particular) prove they don't regress the
  vulnerability surface.
- **Capturing only viewport-sized screenshots** to reduce PNG size — rejected: the
  Chrome DevTools Protocol tool supports `fullpage: true` and the orchestrator
  explicitly invited it; full-page captures expose layout shifts in below-the-fold
  content that 800px-clipped screenshots would hide.
- **Using a project-local `.worktrees/` directory** — rejected: would require adding
  the directory to `.gitignore` and committing that to `main` before the worktree can
  be created safely. Using `~/.config/superpowers/worktrees/eliotik.github.io/` keeps
  the worktree fully outside the project tree and avoids touching `main`, which the
  orchestrator forbids.

This task does not implement any risk-register entry directly; it is the *evidence
substrate* against which R1 (Tailwind 4 typography), R2 (Astro 5 content layer), R3
(React 19 ref handling), and R4 (`@astrojs/tailwind` deprecation) will be evaluated
in their respective tasks.

## 9. Defect resolutions

### D1: Inconsistent screenshot widths

- **Defect file:** `defects/T-00-D1.md`
- **Root cause:** the original capture used the chrome MCP tool's `fullpage: true`
  mode, which (as confirmed empirically — see "Investigation" below) sizes the output
  PNG to the rendered document's intrinsic content extent rather than to the
  configured viewport width. On the carousel post the prose-column layout has an
  intrinsic content width of ~156 px when the document is laid out without a viewport
  width constraint applied to the capture pass; on wider index pages it expands to
  1800 px (the MCP's max-output-pixel side). Net result: 10 PNGs at 6 different
  widths, none of them the documented 1280 px.
- **Fix:** dropped `fullpage: true` and capture each route in **viewport mode** at
  viewport `1280 × 1800` (`deviceScaleFactor: 1`). Width is now uniform at 1280 px
  across all 10 PNGs; height is 1800 px (the maximum the MCP renders without
  applying max-output-pixel downscaling). Between captures the browser is reset via
  `navigate about:blank` so each new route starts at scrollY=0 — necessary because
  resizing the viewport on a previously-scrolled page leaves scrollY past the
  carousel.
- **Resolution commit:** see `backlog.yaml.commit_sha` after the D1 fix commit lands
  (the work commit cannot self-reference its own SHA; the canonical record is
  `backlog.yaml`).

**Investigation (kept for future reference):** I ran two control captures on the
carousel post URL with the chrome MCP. Viewport-mode at `1280 × 800` produced
`1280 × 800`. Setting viewport to `1280 × 4000` and capturing in viewport mode
produced `576 × 1800` — the MCP downscales any output whose longest side exceeds
~1800 px, preserving aspect ratio. `1280 × 1800` is therefore the largest
viewport-mode CSS-pixel rectangle that survives the round-trip without downscaling
or width drift.
