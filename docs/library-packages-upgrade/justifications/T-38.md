## 1. Goal recap

Bump Astro from 6.1.10 to 6.2.1 and apply the dev-toolbar disable fallback to eliminate recurring `504 Outdated Optimize Dep` errors caused by a race between Vite's dependency optimizer and Astro's dev-toolbar dynamic imports on every cold-start in development mode.

- `package.json` — `astro` bumped from `6.1.10` to `6.2.1` in dependencies.
- `pnpm-lock.yaml` — lockfile updated to reflect the new Astro version and any transitive dependency changes.
- `astro.config.mjs` — added `devToolbar: { enabled: false }` (D1 fallback fix). Production output unaffected (toolbar is dev-only).
- `docs/library-packages-upgrade/backlog.yaml` — T-38 status `backlog` → `in-progress` → `qa-pending` → `defect` → `qa-pending`.
- `docs/library-packages-upgrade/defects/T-38-D1.md` — defect resolved.

## 3. Why this approach

This task implements the Astro minor-version bump described in the upgrade backlog (T-38). The 6.1.x line had a known race between Vite's dependency optimizer re-bundling and Astro's dev toolbar dynamic imports, causing `504 Outdated Optimize Dep` responses on every cold-start for the toolbar chunk families (`ui-library-`, `audit-`, `xray-`, `toolbar-`, `settings-`, `dev-toolbar/entrypoint.js`). Astro's dev-server update notice flagged 6.2.1 as available, so the bump-first approach was attempted.

**However, QA's PerformanceObserver-based measurement (defect T-38-D1) showed the bump alone is insufficient — 6.2.x still races on cold-start (6 × 504 on `/`, 1 × 504 on the user-reported post URL).** The original prompt explicitly authorized the fallback path: adding `devToolbar: { enabled: false }` to `astro.config.mjs`. With the toolbar disabled, its dynamic-import chunks (`audit`, `xray`, `toolbar`, `ui-library`, `settings`, `dev-toolbar/entrypoint.js`) are never registered and therefore cannot 504. The fallback is dev-only — production is untouched.

No peer packages required bumping: all `@astrojs/*` packages, `astro-expressive-code`, and `@expressive-code/*` remain compatible with Astro 6.2.1 at their current versions. The only peer warning from `tsconfck` (wanting `typescript@^5.0.0`) is benign since TypeScript 6.0.3 (already installed, a newer major) fully satisfies the requirement. A React peer warning from `quicklink` inside `@divriots/jampack` is pre-existing and unrelated to this task.

## 9. Defect resolutions

### D1: bump alone insufficient — 7 × 504 still produced on cold-start
- Defect file: `defects/T-38-D1.md`
- Root cause: Astro 6.2.x retains the dev-toolbar dynamic-import race with Vite's optimizer on cold start. The optimizer's "reloading" event invalidates the `?v=<hash>` query on already-issued chunk requests; those requests then 504 because the new optimized bundle has a fresh hash. Original dev-side measurement used a `window.fetch` monkey-patch installed *after* navigation, which cannot observe Vite's pre-instrumentation HMR boot fetches — that's why it falsely reported `count504: 0`.
- Fix: applied the prompt-authorized fallback `devToolbar: { enabled: false }` in `astro.config.mjs`. With the toolbar disabled, none of the toolbar chunk dynamic imports are issued, so the race window doesn't open. Production output is unaffected (verified bytewise-identical jampack totals).
- Resolution commit: `b8e9018`
- Re-verification using `PerformanceObserver({type: 'resource', buffered: true})` (the methodology QA recommended):
  ```
  Route 1 (cold-start /):                  {"errorCount": 0, "errors": [], "toolbarRequestCount": 0, "totalRequests": 24}
  Route 2 (post user reported):            {"errorCount": 0, "errors": [], "toolbarRequestCount": 0, "totalRequests": 46}
  ```
  Before: 7 × 504. After: 0 × 504.
