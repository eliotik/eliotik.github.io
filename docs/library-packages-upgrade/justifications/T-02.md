## 3. Why this approach

Implements design §2 CI/CD finding 2 ("Node pinned to 18.19.0 (EOL April 2025)") and plan task `#task-t-02`. Resolves the EOL-runtime risk that blocks every later task. Considered alternatives:
- **Pin to 22.x (range)** instead of an exact version — rejected: the plan and §2 finding 2 explicitly call for a single exact version string in all four files to avoid drift (and `actions/setup-node` semantics differ between exact vs range).
- **Jump to Node 24** — rejected: Node 24 is not yet LTS as of 2026-04-29; the plan target is "current 22 LTS minor".

Resolved version `22.22.2` was determined via `nvm version lts/jod`. Touches risk register entry **R7** (sharp pin under newer Node): the existing `sharp@0.32.6` pin still installs and the production build still passes under Node 22.22.2 — full sharp unpin is intentionally deferred to T-20/T-26.
