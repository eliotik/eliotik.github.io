## 1. Goal recap

Eliminate the duplicate "Copy" button that becomes visible when scrolling a code snippet to the right end, leaving only Expressive Code's native floating top-right copy icon as the user-facing copy affordance.

## 2. What changed

- `src/layouts/PostDetails.astro` — Removed the entire `attachCopyButtons()` function (49 lines, including the inner `copyCode` helper) and its invocation in `initPostDetails()`. The function imperatively appended a `<button class="copy-code absolute right-3 -top-3 ...">Copy</button>` to every `<pre>` and wrapped the `<pre>` in a `<div style="position: relative">`. After the Astro 6 / Expressive Code 0.41.7 upgrade (T-30), `astro-expressive-code` now provides its own native floating top-right copy icon (`plugin-frames`), making the manual implementation redundant and visually broken at scroll-end.

## 3. Why this approach

This task implements design §1 criterion 5 (routes render correctly) by removing the copy-button regression introduced by the Astro 6 / Expressive Code upgrade. Investigation traced the regression to two interactions: (1) the manual `attachCopyButtons()` appended its `<button>` as a child of `<pre>` rather than the wrapper `<div>`, and (2) Expressive Code 0.41.7's CSS reset rule `.expressive-code *:not(:is(svg, svg *)) { all: revert; box-sizing: border-box }` reverts the Tailwind `absolute` class's `position: absolute` declaration to the browser default `position: static` for any descendant of `.expressive-code`. With `position: static`, the manual button rendered inline inside the `<pre>` (which has `overflow-x: auto`), hidden from view in the default state but revealed when the user scrolled the code horizontally. Two alternatives were considered: (a) move `appendChild(copyButton)` to the wrapper div and add CSS isolation against EC's reset — rejected because it would leave two copy buttons per block, contradicting the task's explicit requirement that "only the floating top-right icon copy button should exist"; (b) disable EC's native copy button via plugin config — rejected because the user explicitly wants the native icon. Removing the manual implementation entirely satisfies both the visual-regression fix and the user-stated UX preference, and reduces the JavaScript surface area on every post page (one fewer DOM mutation pass on load). No risk register entry from design §6 directly applies; this is a regression patch tied to the EC upgrade in T-30.

## 7. Risks introduced or accepted

- **UX change**: Expressive Code's tooltip-style "Copied!" feedback replaces the previous in-button "Copy" → "Copied" text swap. Users now see a small green tooltip after clicking the icon. This matches the task's stated requirement ("only the floating top-right icon copy button should exist") and is the canonical EC UX pattern.
- **Wrapping `<div>` removed**: The manual `attachCopyButtons()` also wrapped each `<pre>` in a `<div style="position: relative">`. That wrapper is no longer created. Expressive Code generates its own `<figure class="frame">` wrapper (verified via DOM inspection: 35 frames for 35 pres on the test post), which provides the positioning context EC's own copy button needs (`inset-inline-end` on `.copy` is relative to `.frame`). No layout regression introduced.
- **Tab focus**: The manual code also set `tabindex='0'` on each `<pre>`. EC's `<pre>` has its own `tabindex='0'` attribute baked in (verified in EC's `core/dist/index.js`), so keyboard scrollability is preserved.
