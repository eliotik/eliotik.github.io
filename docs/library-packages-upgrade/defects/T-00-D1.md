## Summary

Captured baseline PNG widths do not match the viewport documented in `SCREENSHOTS.md` ("1280 × 800, scale 1, full page"); several screenshots — most importantly the two highest-risk diff targets (`03-post-with-images.png` and `04-post-with-carousel.png` at **156 × 1800**) — are far too narrow to serve as a meaningful visual baseline for downstream tasks.

## Reproduction

1. `git checkout upgrade/T-00-baseline`
2. `file docs/library-packages-upgrade/baseline/*.png`
3. Compare reported widths to the viewport claim in `docs/library-packages-upgrade/baseline/SCREENSHOTS.md`.

## Expected behavior

Per `2026-04-29-upgrade-plan.md` Task T-00 step 6 ("Capture each route at viewport 1280×800") and `SCREENSHOTS.md` line 21 (`Viewport | 1280 × 800, scale 1, full page`), every captured PNG should have a width consistent with a 1280-px viewport (i.e. 1280 px at scale 1, or a uniform multiple thereof if the capture used a higher device-pixel ratio).

The baseline is referenced by:
- `2026-04-29-upgrade-design.md` §1 success criterion 5 (route rendering)
- `2026-04-29-upgrade-design.md` §6 risks R1 (Tailwind 4 typography), R3 (React 19 carousel/refs), R4 (`@astrojs/tailwind` deprecation)
- `2026-04-29-upgrade-plan.md` §3 verification (`baseline/<route>.png × 10`)
- The justification §3, which explicitly names these screenshots as the "evidence substrate" for R1–R4

A baseline whose width is inconsistent across pages, and is far below the viewport on the carousel post, can't fulfill that role: visual smoke at T-10/T-11/T-20/T-21/T-22/T-30 will diff a 1280-px-wide capture against a 156-px-wide baseline, which is a meaningless comparison for the carousel — exactly the highest-visual-risk component in the campaign (T-10 replaces it with CSS scroll-snap).

## Actual behavior

The 10 captured PNGs have non-uniform widths, none of which is 1280 px:

```

02-posts-index.png:         1800 x 1561
03-post-with-images.png:     156 x 1800   <-- carousel-adjacent risk target
04-post-with-carousel.png:   156 x 1800   <-- direct R3 / T-10 evidence target
05-tips-index.png:          1800 x 1155
06-tags-index.png:           804 x 1800
07-tag-detail.png:          1800 x 1729
08-threads-index.png:       1654 x 1800
09-about.png:               1379 x 1800
10-404.png:                 1800 x 1135
```

Six widths > 1280 (suggesting an effective `deviceScaleFactor` ≈ 1.41), four widths < 1280 (suggesting the capture occurred against a layout intrinsic-content width rather than viewport width). Heights uniformly capped at ≤ 1800 px or matching the fullPage extent.

For the two narrow-width PNGs:
- **`03-post-with-images.png` (156 × 1800):** body text and tables are visible but rendered at an unrepresentative narrow column — most inline images are too small for layout regression detection.
- **`04-post-with-carousel.png` (156 × 1800):** the `<ImageSlider>` Carousel is identifiable as a vertical sequence of phone-shaped thumbnails, but slide controls (dots, arrows), aspect ratios, captions, and slide-transition spacing are unreadable at this width — i.e. the high-risk visual element targeted by R1/R3 cannot be diffed.

Visual evidence (all observed during this QA pass): see `docs/library-packages-upgrade/qa-runs/T-00-20260429T155046Z/` for the QA run logs; the PNGs themselves are at the paths listed above.

## Files implicated

## Suggested fix direction (optional)

Two acceptable resolutions; either fixes the defect:

1. **Re-capture the screenshots at a uniform width** (1280 px CSS, or 1280 × `deviceScaleFactor` consistently across all 10) — this is the cheapest path and is what `SCREENSHOTS.md` already promises. Ensure the headless capture sets the viewport before navigation, and that any "fullPage" mode preserves viewport width.
2. **Update `SCREENSHOTS.md` to faithfully describe what was captured** (per-image widths and the actual `deviceScaleFactor`/capture mode used). This is acceptable only if the captured widths are in fact what later tasks should diff against — i.e. T-10/T-30 will deliberately re-capture at the same non-uniform widths. Given the carousel is captured at 156 px wide, this is unlikely to be the right call.

QA expects the dev to choose (1) and re-take the 10 PNGs at a consistent, viewport-correct width. No source code changes are required, and the audit baseline file (`audit-baseline.txt`) is unaffected and need not be re-run.
