## Summary

The GitHub Pages deploy workflow fails immediately in the `build` job with a pnpm version conflict error when `withastro/action@v6` sees both a `package-manager: pnpm@latest` input in the workflow YAML and a `"packageManager": "pnpm@10.33.2"` field in `package.json`. The action rejects the ambiguity and refuses to proceed.

**Workflow run URL:** https://github.com/eliotik/eliotik.github.io/actions/runs/25214297859

## Reproduction

1. Push the current `main` (at `5cc9182`) to `origin/main`.
2. The "Deploy to GitHub Pages" workflow triggers.
3. The `build` job fails at step "Install, build, and upload your site" with:
   ```
   Error: Multiple versions of pnpm specified:
     - version latest in the GitHub Action config with the key "version"
     - version pnpm@10.33.2 in the package.json with the key "packageManager"
   Remove one of these versions to avoid version mismatch errors like ERR_PNPM_BAD_PM_VERSION
   build: .github#86
   ```

## Root cause

Task T-27 upgraded `withastro/action@v3` → `@v6`. The `@v6` version of `withastro/action` introduced strict validation that rejects a mismatch between:
- The `package-manager` input in the workflow YAML (`pnpm@latest`).
- The `packageManager` field in `package.json` (`pnpm@10.33.2`, set by T-03 during the pnpm Corepack migration).

`withastro/action@v3` accepted `pnpm@latest` silently and resolved to whatever pnpm version was available. `@v6` treats any conflict between the YAML input and `package.json` as a fatal error.

This was not caught during T-27 QA because T-27 only verified the YAML parses correctly in the repository — it did not trigger a real workflow run (the branch was not pushed to `origin/main` and no `workflow_dispatch` was issued).

## Files implicated

- `.github/workflows/deploy.yml` — line 32: `package-manager: pnpm@latest` must be changed to `pnpm@10.33.2` to match `package.json`, OR the `package-manager` input must be dropped entirely so `withastro/action@v6` reads `pnpm@10.33.2` directly from `package.json`.

## Suggested fix direction

**Option A (recommended):** Remove the `package-manager` input from the workflow YAML and let `withastro/action@v6` auto-detect it from `package.json`'s `packageManager` field. This is the idiomatic `@v6` pattern.

**Option B:** Pin the workflow input to `package-manager: pnpm@10.33.2` to match `package.json` exactly.

Either option is a one-line change. Option A is preferred because it keeps the workflow self-consistent with the authoritative `packageManager` field in `package.json` (no need to update both when pnpm bumps).

Note: `withastro/action@v6` also auto-enables Corepack, so the explicit `Enable Corepack & pnpm` step (lines 23–27) may become redundant — the followup task should verify.
