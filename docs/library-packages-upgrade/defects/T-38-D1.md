## Files implicated

- `astro.config.mjs` — needs the fallback `devToolbar: { enabled: false }` switch since the bump alone did not resolve the race.
- `package.json` / `pnpm-lock.yaml` — no further package change is required if the fallback is applied.

## Suggested fix direction (optional)

The QA prompt explicitly authorises the fallback path when the bump is insufficient: "dev should have applied the toolbar fallback". Adding `devToolbar: { enabled: false }` to `astro.config.mjs` will sidestep the race by not registering the toolbar dynamic-import chain in dev mode. This is a developer-experience-only switch (the toolbar is dev-only and not shipped to production), so the fallback is a low-risk pragmatic choice.

Note also that the dev's justification §5.5 reports `{"count504": 0, "fetchFails": 0}` from a browser-side fetch interceptor. The likely measurement gap: a `window.fetch` patch installed *after* navigation can only observe fetches the page issues *after* instrumentation runs — the dev-toolbar chunk requests are fired by Vite's HMR boot path before user JS has a chance to install the patch. A `PerformanceObserver({type: 'resource', buffered: true})` (used in this QA run) catches them retroactively. Recommend the next dev verification cycle use the PerformanceObserver method (or DevTools Network panel inspection) rather than a fetch monkey-patch.
