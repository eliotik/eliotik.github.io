## Summary

QA prompt's Step 6 / pass-criteria require `/posts/1/` and `/tips/1/` to return 200 (and `dist/posts/1/index.html` / `dist/tips/1/index.html` to exist) after redirect removal. ## Actual behavior

- `dist/posts/1/index.html` does NOT exist after `pnpm build`.
- `dist/tips/1/index.html` does NOT exist.
- `GET /posts/1/` returns HTTP 404 in dev server.
- `GET /tips/1/` returns HTTP 404 in dev server.

The dev's justification §5.4 acknowledges this and explains it is by design:

> "Astro pagination does not generate page 1 as a separate directory; page 1 content lives at `dist/posts/index.html` and `dist/tips/index.html`."

Architectural source confirmed at `src/pages/posts/[slug]/index.astro` line 25:

```ts
const pagePaths = getPageNumbers(posts.length)
    .filter(pageNum => pageNum !== 1) // Exclude page 1, it's served by /posts/index.astro
    .map(pageNum => ({
        params: { slug: String(pageNum) },
    }));
```

There is no `[...page].astro` route. Page 1 has never been independently routed in this codebase — it is duplicate content with `/posts/`. Prior to this PR, the `redirects` block in `astro.config.mjs` mapped `/posts/1` → `/posts/`. The dev removed that block to silence the `[router]` collision warning that T-33 was tasked with fixing. Side-effect: external links to `/posts/1` now 404 instead of 301.

The QA-prompt author appears to have assumed pagination would re-emit page 1 once redirects were removed; the existing pagination code explicitly does not.

## Suggested fix direction (optional)

This is a decision point for the orchestrator, not a clear implementation defect. Three options to satisfy the literal pass criterion, each with downsides — orchestrator should choose:

1. **Accept dev's option A as-is (recommended).** The dev's justification §7 documents this trade-off explicitly. Page 1 was always duplicate content; external inbound links to `/posts/1` are unlikely (sitemap and feeds reference `/posts/` and slug-form URLs, not numeric page-1 URLs). Override the literal pass criterion analogous to the Fix 2 pre-authorization. Approve and merge.
2. **Restore redirects with a different mechanism.** Use a 301 in `dist/_redirects` (Netlify) or in the GitHub Pages 404 fallback page. Note: GitHub Pages does not honor server-side redirects; this would require a static `<meta http-equiv="refresh">` page. Adds complexity for a low-traffic edge case.
3. **Add a dedicated `src/pages/posts/1/index.astro` that re-exports the index page.** Re-introduces the routing collision warning T-33 was created to fix; not viable without further routing changes.

Recommend option 1 (orchestrator override). Severity is Low because functionality is intact: the site builds, all live URLs work, sitemap is unaffected, and the only regression is two legacy-redirect URLs returning 404 instead of 301 to identical content.
