## Summary

`estimateReadTime` always returns `1` because the Astro 6 Content Layer API no longer exposes `post.body`; this regression is user-visible on every `/threads/<slug>` detail page where "Read time" displays the article-count instead of an actual word-count-based estimate.

## Reproduction

1. `git checkout upgrade/T-20-astro-5`
2. `pnpm install --frozen-lockfile`
3. `pnpm dev`
4. Navigate to `http://localhost:4321/threads/five-systems-of-engineering-management` (a thread with 7 long-form articles, each post is several thousand words).
5. Observe the "READ TIME" stat in the article header.

## Expected behavior

Per design §1 success criterion 5, "Local dev server renders correctly on these routes: `/threads`, ..." — the rendered values must reflect the underlying data accurately.

Per the previous behavior on `main` (commit `f9e142a`), `estimateReadTime` parses each post's body markdown, strips code blocks/inline code/markdown punctuation, and computes `ceil(words / 200)` per article. For a 7-article thread of long-form posts, the displayed total read time should be in the 30–60+ minute range, matching the actual reading load.

## Actual behavior

`/threads/five-systems-of-engineering-management` displays:

```
READ TIME
7 min
```

(For a thread containing 7 articles totalling many thousands of words.)

The number always equals the article count, because `estimateReadTime(undefined)` short-circuits at line 32 and returns `1` for every post; `totalReadTime` is then `articleCount * 1`.

Screenshot: `docs/library-packages-upgrade/qa-runs/T-20-20260429T213307Z/visual/08b-thread-detail.png`

This affects every thread detail page (currently 2 threads — `five-systems-of-engineering-management` shows `7 min`, `flutter-and-google-maps` shows `4 min`).

const estimateReadTime = (body: string | undefined): number => {

## Files implicated

- `src/utils/getThreadDetail.ts:66` — `estimateReadTime(undefined)` is called unconditionally because the dev removed the previous `post.body` reference (Content Layer doesn't expose `body` on the `CollectionEntry` shape directly).
- `src/utils/getThreadDetail.ts:31` — The `estimateReadTime` function still works correctly when given a string; only the caller is broken.
- `src/layouts/ThreadDetail.astro:41` — Renders `{detail.totalReadTime}` to the page header on every `/threads/<slug>` route.

## Suggested fix direction (optional)

Several non-prescriptive options exist; the Dev Agent should pick whichever best fits the campaign's scope:

- Use Astro 6 Content Layer's `render(post)` to access the compiled HTML / processed content, then estimate from that. (`render()` is already imported in `PostDetails.astro` post-T-20 — same pattern works in a utility.) Note `getThreadDetail` is currently synchronous; this approach would require making it async.
- Add a small custom transform in the `glob` loader (`src/content.config.ts`) that reads the raw markdown file off disk and stores `wordCount` on the entry for downstream use.
- Precompute and persist a `readTime` (or `wordCount`) field in each post's frontmatter, then read `post.data.readTime` in `getThreadDetail.ts`. (Schema would need to gain an optional `readTime: z.number().optional()`.)
- If the read-time stat is not worth the migration cost, remove the "Read time" `<dl>` cell from `ThreadDetail.astro` and drop `totalReadTime` from `ThreadDetail` / `ThreadArticle` types entirely.
